# Database notes

Why each constraint and index exists. Phase 3 appends query plans and measured timings here.

## Module tables (Phase 4)

Common to every module table: UUIDv7 `id`, `project_id` (cascade), `created_by_id` (restrict), `created_at`, `updated_at` (trigger), and an index on every foreign key column. Optional links to subprojects, sprints and releases use composite `(project_id, x_id)` foreign keys named `<table>_project_<column>_fk`, so a row can never point at another project's subproject, sprint or release. Optional links null only their own column on delete (`ON DELETE SET NULL (col)`); the two NOT NULL subproject links use `RESTRICT`.

Human-readable codes: `code_counters (project_id, scope, last_value)`. `nextSeq(tx, projectId, scope)` upserts the counter inside the same transaction as the insert, so concurrent writers queue on the counter row. A rolled-back insert burns a number (gap tolerant), numbers are never reused. `code` is a generated stored column, padded with `repeat('0', greatest(n - length(seq::text), 0))` so values above the pad width are never truncated (`USM-100`, not `USM-10`).

## Read models and search (Phase 3)

Migration `0007_search_trigram`: `CREATE EXTENSION pg_trgm` (a trusted extension, so the database owner can install it) and GIN trigram indexes on `activities.title`, `subprojects.name`, `subprojects.code` and `users.full_name`. They serve `ILIKE '%term%'` and the `%` similarity operator for the typeahead; trigram indexes need three characters, so activity search starts at three and shorter input only searches subproject codes and people.

No other index was added: the plans below use only indexes that already existed. Full plans, the seed size and the timings are in [db-plans.md](db-plans.md), generated by `npm run db:explain -w @myapp/backend` against `npm run db:seed:perf` (50,064 activities, 81,644 events). The generator fails loudly in its summary if any plan shows a sequential scan on `activities`; none does.

| Query                 | Index access on `activities`                                                                                                                                    | Median server time |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| Home, team member     | bitmap scans of `activities_assignee_due_open_idx` (open, dated work) and `activities_completed_at_idx` (done this week)                                        | about 41 ms        |
| Home, project manager | bitmap scans of `activities_due_open_idx` and `activities_completed_at_idx`                                                                                     | about 79 ms        |
| Portfolio             | `activities_subproject_id_idx` per subproject (lateral aggregate), `activities_release_id_idx` for the next release, primary-key probes for unfinished blockers | about 57 ms        |
| Workload              | `activities_assignee_id_idx` per person, primary-key probes for unfinished blockers                                                                             | about 28 ms        |
| Search, activities    | `activities_title_trgm_idx` (two bitmap scans: ILIKE and similarity, OR-ed)                                                                                     | about 60 to 80 ms  |

Decisions and findings:

- Unfinished blockers ("waiting on dependency"): the first version joined `activity_dependencies` to `activities` with a plain join, and the planner hashed all 15,000 open activities (a sequential scan). The `waiting` CTE now starts from the small dependencies table and probes `activities` by primary key through a `LIMIT 1` lateral subquery, which also stops the planner from flattening it back into a hash join. Portfolio and Workload share it (`WAITING_CTE_BODY`).
- Home: open work more than 60 days overdue no longer appears on Home (`OVERDUE_LOOKBACK_DAYS`); it still counts in Portfolio. Home caps at 1,000 rows (`HOME_ROW_LIMIT`) and returns `truncated: true` when the cap is hit, which a PM sees on an unfiltered view of a very large project; narrowing by assignee or subproject avoids it.
- Portfolio computes everything in one SQL statement (lateral aggregates per subproject), not per-row queries. Health is changed through the existing `PATCH /subprojects/:id`.
- `openHighRaid` is wired to `raid_items` (open or in progress, impact High) because the Phase 4 tables already exist; the plan's "returns zeros until the RAID table exists" stub is therefore not needed.
- Workload orders people alphabetically, exposes counts against limits only, and has no ranking or output-score field (a test asserts this).
