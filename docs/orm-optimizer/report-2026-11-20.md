## Finding details

### 1. unbounded read per request - `apps/backend/src/services/workItemService.ts:115` (Medium, Static only, access layer: drizzle)

- **What the code does:** `loadWorkItems` runs six parallel selects (OST solutions, USM features, Kano requests and specs, RAID items and mitigating actions) plus project activities (`apps/backend/src/services/workItemService.ts:90`), each joined to `projects` with only an "not archived" filter, then classifies and buckets every row in memory.
- **Plan evidence:** not Verified. The RAID mitigating-actions read was explained: node `Nested Loop`, estimated 3 vs actual 3 rows, 0.043 ms recorded, 3 shared hits, all tables under 10 rows (`docs/orm-optimizer/plans/work-items-raid-actions.json`). The data is too small to show the growth problem.
- **Why it matters:** it runs on every Home load (`apps/backend/src/services/homeService.ts:137`), every Workload load (`apps/backend/src/services/workloadService.ts:39`) and every project page load (`apps/backend/src/services/workItemService.ts:314`). Row count is all-time, including completed items, so request cost may grow linearly with project history.
- **Suggested fix (not applied):** filter in SQL to open items and items completed inside the reporting window. For the KPI strip, compute `count(*) FILTER (...)` per status in SQL instead of loading every row. Keep the full-row load only for the rows the page lists.
- **Other sites in this group:** `apps/backend/src/services/workItemService.ts:119`, `apps/backend/src/services/workItemService.ts:128`, `apps/backend/src/services/workItemService.ts:133`, `apps/backend/src/services/workItemService.ts:139`, `apps/backend/src/services/workItemService.ts:144`, `apps/backend/src/services/workItemService.ts:150`

### 2. large result capped by LIMIT - `apps/backend/src/services/homeService.ts:61` (Medium, Static only, access layer: drizzle)

- **What the code does:** the Home candidate query now returns every open dated activity (no overdue lookback, no future horizon) plus items done this week, ordered by due date and capped at `HOME_ROW_LIMIT` = 1,000 (`apps/backend/src/services/homeService.ts:35`).
- **Plan evidence:** not Verified. PM and team-member variants were explained with actor `01a1f362-3342-7a67-9df9-79df217a30aa` and ranges for 2026-11-20: node `Limit`, estimated 1 vs actual 0 rows, 0.050 ms and 0.052 ms recorded (`docs/orm-optimizer/plans/home-pm.json`, `docs/orm-optimizer/plans/home-member.json`). `activities` has 0 rows locally.
- **Why it matters:** with a large backlog the PM view may read up to 1,000 rows and a `waitingOnDependency` lookup over the same ids on each load. The partial indexes `activities_due_open_idx` and `activities_assignee_due_open_idx` (`apps/backend/src/db/tables/activities.ts:63`) should serve it, but that is unconfirmed.
- **Suggested fix (not applied):** rerun this query with the perf seed and check that it uses the partial index without a sort. If the Later bucket makes the result large, load Later on demand.
- **Other sites in this group:** none
